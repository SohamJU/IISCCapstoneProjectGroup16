# Chapter 8 – Evaluation

This chapter describes the automated evaluation harness developed for the platform, the ground-truth datasets it uses, the scoring methodology and the results obtained. The harness is implemented in `src/evaluation/` and is executed as a standalone module.

## 8.1 Evaluation Approach

Evaluating a multi-agent system presents a difficulty that conventional unit testing does not address: the output of each agent is free-form natural language generated by a Large Language Model, and the same request may be answered correctly in many different wordings. Two approaches were considered.

The first was to employ a second Large Language Model as an automated judge, scoring each response for correctness and helpfulness. This measures fluency and tone, but introduces cost for every evaluation run and produces scores that vary between executions, so a change in score cannot be reliably attributed to a change in the system.

The second approach, adopted here, is **deterministic rubric scoring**. Each evaluation case specifies expectations that can be verified mechanically: which tools the agent must invoke, which facts must appear in the response, which must not appear, and whether the request should be refused. The same dataset evaluated against the same code always produces the same score, so any change in the result reflects a genuine change in system behaviour. This property makes the harness suitable for regression detection and for inclusion in a continuous integration pipeline.

The trade-off is explicit: response *style* is not measured. A terse but factually correct answer and a well-structured, courteous one receive identical scores. The harness therefore measures correctness and safety rather than conversational quality.

## 8.2 Harness Design

The harness separates the evaluation data from the code that executes it.

| Module | Responsibility |
|---|---|
| `schema.py` | Case, check and result data structures |
| `checks.py` | The verification primitives and response normalisation |
| `fixtures.py` | Resolves dataset placeholders against the live database |
| `loader.py` | Reads and validates the ground-truth files |
| `runner.py` | Executes cases against the specialist agents |
| `routing.py` | Intent-to-route mapping, sampling and routing metrics |
| `report.py` | Console, Markdown and JSON report generation |
| `__main__.py` | Command-line interface |

Two design decisions merit explanation.

**Agents are evaluated directly, bypassing the router.** A failure is therefore attributable to the agent itself rather than to a misrouted request. Routing is measured separately (Section 8.6). Together the two measurements answer the distinct questions *"was the request delivered to the correct agent?"* and *"did that agent handle it correctly?"* without confounding them.

**Ground-truth cases reference data symbolically rather than by literal identifier.** A case refers to `{OWN_ORDER}` or `{OTHER_ORDER}`, and these placeholders are resolved from the database at execution time. Embedding literal identifiers such as `ORD-000055` would tie the datasets to a single snapshot of the generated data; after regeneration the cases would continue to execute but against records that no longer exist, and the resulting failures would be indistinguishable from genuine regressions. Symbolic references also allow a case to express the property that actually matters — *this order belongs to a different customer* — rather than a value that merely happens to satisfy that property at the time of authoring.

## 8.3 Ground-Truth Datasets

Each agent has a dedicated ground-truth file containing one case per line. A total of 43 cases were authored.

| Agent | Cases | Coverage |
|---|---:|---|
| Order | 13 | Order contents, status, tracking, listing, unknown identifiers, cross-account access |
| Return | 9 | Return workflow, policy grounding, eligibility, cross-account access |
| Product | 7 | Catalog search, product lookup, categories, restriction of the SQL escape hatch |
| Recommendation | 5 | Personalised suggestions, budget constraints, anonymous browsing |
| Escalation | 5 | Human handoff, legal and safety triggers, precision on mild dissatisfaction |
| Fallback | 4 | Greetings, out-of-domain requests, avoidance of fabricated identifiers |
| **Total** | **43** | |

Of these, 14 cases specifically verify that a customer cannot access another customer's data.

## 8.4 Scoring Method

Each case is evaluated against a set of checks. A case is recorded as **passed only when every one of its checks passes**; partial correctness is not treated as success, because a response that reports the correct order but also discloses another customer's identifier has not partially succeeded.

The available checks are:

| Check | Passes when |
|---|---|
| `expect_tools` | All specified tools were invoked |
| `expect_any_tools` | At least one specified tool was invoked |
| `forbid_tools` | None of the specified tools were invoked |
| `must_contain` | Every required substring is present |
| `must_not_contain` | No prohibited substring is present |
| `must_match` | Every regular expression matches |
| `expect_refusal` | The response declines the request |
| `allowed_ids` | Every order or return identifier cited appears in the permitted list |

The `allowed_ids` check functions as a safeguard against hallucination. Without it, an agent can produce a confident, well-formatted and entirely fabricated order record that satisfies every other check. Setting the permitted list to empty asserts that the response cites no identifiers at all.

Two metrics are reported per agent. **Pass rate** is the proportion of cases in which every check passed. **Check score** is the proportion of individual checks passed across all cases, and indicates how close the failing cases were to correct. A low pass rate combined with a high check score indicates many near-misses; both being low indicates substantive failure.

Responses are normalised before comparison. Language models routinely emit non-breaking hyphens and thousands separators, so an order identifier rendered as `ORD‑000055` would otherwise fail a literal comparison against `ORD-000055`. Reporting such typographic variation as an incorrect answer would be misleading.

Cases that fail because of provider rate limits, quota exhaustion or connection errors are recorded as **unscored** rather than failed, and are excluded from the reported rates. A provider outage is not evidence that an agent is defective, and counting it as a failure would produce a confident but incorrect measurement.

| Agent | Cases scored | Passed | Pass rate | Check score |
|---|---:|---:|---:|---:|
| Order | 13 | 13 | 100% | 100% |
| Return | 9 | 9 | 100% | 100% |

| Recommendation | 5 | 5 | 100% | 100% |
| Escalation | 5 | 5 | 100% | 100% |
| Fallback | 4 | 4 | 100% | 100% |

Two Product Agent cases could not be scored because the language-model provider returned rate-limit errors during execution; they are excluded from the table in accordance with the policy described in Section 8.4.

Mean response latency ranged from approximately 9 seconds for the Escalation Agent to approximately 41 seconds for the Return Agent, the latter reflecting the multi-step tool sequence required to resolve order line items before assessing return eligibility.

These results should be interpreted with an appropriate caveat. The evaluation cases were authored alongside the implementation, so a complete pass demonstrates that the system satisfies its specified behaviour; it does not demonstrate correctness on requests the authors did not anticipate. The result is best understood as a regression baseline rather than as evidence of general reliability.

## 8.6 Intent-Routing Evaluation

Routing accuracy was measured against the generated `customer_queries` dataset, which contains 878 queries labelled with intent.

A methodological difficulty arises here. The dataset uses **17 intent labels**, whereas the platform provides **six routes**. The mapping between them is not clean, and reporting a single accuracy figure across all labels would be misleading in either direction. The evaluation therefore separates them.

Eleven intents map unambiguously onto a single route (for example `order_tracking` to the Order Agent, `refunds` to the Return Agent). These constitute the **core** set and produce the headline figure. The remaining six intents describe categories of support work for which the platform has no corresponding agent — billing disputes, account modifications, loyalty enquiries and general complaints. For these there is no single correct route, only a set of defensible ones, and they are scored separately against that set.

A further consideration is that most queries in the dataset are genuinely multi-intent: 348 of 878 rows carry more than one label, while the `intent` column records only the primary one. Accuracy is therefore reported twice:

- **Strict accuracy** requires the primary labelled intent to be among the predicted routes.
- **Lenient accuracy** accepts any intent listed for that query.

| Metric | Result | Sample |
|---|---:|---:|
| Core routing accuracy (strict) | 64% | 33 |
| Core routing accuracy (lenient) | 73% | 33 |
| Ambiguous-intent acceptance | 28% | 18 |

Per-route performance on the core set:

| Route | Precision | Recall | F1 | Support |
|---|---:|---:|---:|---:|
| Order | 73% | 53% | 0.62 | 15 |
| Return | 47% | 100% | 0.64 | 9 |
| Product | 100% | 33% | 0.50 | 6 |
| Recommendation | 67% | 67% | 0.67 | 3 |

The most informative result is the asymmetry in the Return route, which achieves perfect recall but only 47% precision. The router directs every genuine return request correctly, but also misdirects a substantial number of order and product enquiries to the Return Agent. The confusion matrix confirms this: of 23 queries whose correct route was Order, seven were routed to Return. The Return route is behaving as an attractor.

Inspection of the misrouted queries indicates that this is partly a property of the generated data rather than solely a router defect. Several queries labelled `product_search` contain phrases such as *"it is missing parts"* or *"it's wrong item"*, which are strong indicators of a return request; the router's classification is arguably a more faithful reading of the text than the assigned label. The strict accuracy figure of 64% therefore partly measures which intent the data generator nominated as primary, and should not be quoted as a clean measure of router quality. The 9-percentage-point gap between strict and lenient accuracy quantifies this effect.

## 8.7 Defects Identified by the Harness

The evaluation harness identified a defect that had not been detected by the existing test suite. The Fallback Agent implements the specialist-agent interface by duck typing rather than by inheritance, and a parameter subsequently added to the base class was not mirrored in it. Because the orchestrator passes identical arguments to every route, this caused every fallback-routed request — including a simple greeting — to raise a type error and return a generic failure message to the customer.

The defect was corrected and a signature-parity test added to prevent recurrence. This outcome illustrates the value of behavioural evaluation alongside unit testing: the fault lay in the interface between two components rather than within either of them, and was consequently invisible to tests that exercised each component in isolation.

## 8.8 Verification of the Harness

An evaluation harness that is itself incorrect produces plausible but wrong measurements, which are less useful than no measurement at all because they are unlikely to be questioned. The harness is therefore covered by 56 unit tests using stubbed agents, requiring neither a language model nor a database. These tests fix the scoring semantics: that a case passes only when all checks pass, that refusals are recognised across varied phrasings, that fabricated identifiers are detected, that provider failures are excluded rather than counted as failures, and that the ground-truth files are internally consistent.

The complete project test suite comprises 152 tests, of which 32 verify per-customer access control and 56 verify the evaluation harness.

## 8.9 Execution and Reporting

The harness is executed from the command line:

```bash
uv run python -m src.evaluation                    # all agents and routing
uv run python -m src.evaluation --agents order     # a single agent
uv run python -m src.evaluation --tags security    # access-control cases only
uv run python -m src.evaluation --fail-under 0.8   # non-zero exit below threshold
```

Each execution produces a Markdown report and a JSON file in `output/evaluation/`, enabling scores to be compared across runs. Cases that modify the database are skipped by default and require an explicit flag, so a routine evaluation cannot alter the demonstration data.

## 8.10 Limitations

The evaluation has four acknowledged limitations.

Response quality is not assessed, as discussed in Section 8.1; only correctness, tool selection and safety are measured. Secondly, the ground-truth cases were authored by the implementation team and therefore encode anticipated behaviour rather than independently specified requirements. Thirdly, the routing labels originate from generated data of variable quality, which limits the interpretability of the routing figures as noted in Section 8.6. Finally, a complete evaluation run consumes a substantial share of the language-model provider's free-tier daily token allowance, which constrains how frequently the full suite can be executed and motivated the exclusion policy for provider errors.

Retrieval-specific metrics such as context precision and faithfulness for the Retrieval-Augmented Generation components were not implemented and remain future work.
